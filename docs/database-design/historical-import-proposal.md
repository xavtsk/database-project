## Approved decision

We need to choose where external identity mappings and results belong, and how queries should treat repeated rows.

| Option | Benefit | Cost |
| --- | --- | --- |
| Keep everything as CSV and calculate in Python | Smallest code change | Weak relational query demonstration; repeated parsing and identity checks |
| **Add three historical tables in MySQL (recommended)** | Explicit provenance and foreign keys; SQL matchup counts; reproducible exclusions | Requires a small schema extension and audited importer |
| Put the flat CSV rows into MongoDB | Flexible raw storage | Duplicates structured catalogue identities and adds little beyond existing MongoDB battle logs |

Approved tables, scoped only to this dataset:

1. `historical_sources`: primary key `id`, unique `dataset_key`, source URL, licence, download-manifest hash and import timestamp. Treat changed source bytes as a different import version rather than overwriting provenance.
2. `historical_pokemon`: composite primary key `(source_id, external_id)`, original name (nullable), mapping status, nullable FK `pokemon_id` to `pokemon`. Store the original six stats and source type names to preserve historical differences. Store all 800 external entries, including unmapped forms. Enforce source FK and permitted mapping statuses; a mapped status requires a catalogue ID.
3. `historical_combats`: composite primary key `(source_id, source_row)`, ordered first/second/winner external IDs, nullable `duplicate_of_row`. Three composite FKs reference `historical_pokemon`; a source-local self FK identifies duplicate rows. Check distinct participants and a winner equal to one participant. Import valid result rows only; reject and audit the batch on malformed IDs or invalid outcomes. The inspected batch has none.

Implemented policy:

- Keep all 50,000 valid result rows for traceability. Mark each later exact `(first, second, winner)` copy with its first source-row number. Keep reversed participant order separate because it changes first-attacker role.
- Default evidence queries exclude marked duplicate copies and require both participants to have approved mappings: currently 1,589 rows. This is a conservative policy, not proof that the remaining observations are independent. The source does not establish whether identical rows are repeated simulations or duplicated exports.
- Approve only the 150 proposed name/type mappings. Leave the unnamed record and 649 other entries unmapped. Do not add new playable forms or overwrite PokéAPI data.
- Preserve `tests.csv` as raw inspection material only. Never fabricate winners or count it as historical evidence.
- Make reruns idempotent using source version plus source-row keys. Validate all rows before the data transaction. Preserve existing trainers, teams and simulator logs.

The query in `database/relational/queries/historical_matchups.sql` uses `UNION ALL` to express each accepted combat from the first and second participant's perspectives, then `GROUP BY` Pokémon, opponent and first-attacker role. It returns wins, losses and **sample count**, with source and role visible. It does not sort away participant order, merge these results into MongoDB simulator statistics, train a model, or convert the 1v1 rate into a team win probability.

The data is sparse within the original-151 scope. A pair can have no observations, so the UI must show “no historical evidence” rather than 0% wins. Source algorithm, first-attacker advantage, different stats and small samples limit interpretation.

## Import and display

```sh
python -m scripts.setup_databases
python -m scripts.data_import.import_historical
python scripts/run_local.py
```

Setup creates the tables but does not download or import historical CSVs. The separate importer checks the source hashes against the reviewed `data/processed/historical_mapping.json`, revalidates the exact bytes it parses and verifies the 150 approved mappings. It validates duplicate lineage before writes. All data rows commit in one MySQL transaction after schema DDL. A failed batch rolls back its data; DDL can persist because MySQL commits it implicitly. Tests and raw source files are not altered.

Reruns lock the source version, compare its provenance and all stored mapping/result rows to the approved batch, and return `verified_existing` without adding observations. A changed mapping, source or stored dataset is rejected for review rather than silently overwritten. The audit is in ignored `.local/historical-import.json`.

**Battle analytics → External 1v1 matchup evidence** calls `GET /api/analytics/historical?pokemon_id=4&opponent_id=7`. Choose two different catalogue species to view first/second-attacker result counts. Missing observations are shown explicitly; no-source installations show that the dataset is not imported. The source is shared external evidence, whereas the selected profile's MongoDB history remains trainer-specific. Simulator rules/difficulty filters do not apply to these external results.

For a visible example in this inspected version, compare **Venusaur (#3) and Muk (#89)**: two distinct source results exist across participant roles. This is a UI demonstration, not strong evidence or a recommended matchup. The largest unordered-pair sample in the approved base-form subset is only two distinct results.

## Validation limits

MySQL checks enforce positive source rows, distinct participants, participant winners, valid mapping status and duplicate pointers earlier than the current row. Participant foreign keys and these checks are verified by live tests. The importer separately checks that a duplicate points directly to an earlier original with the same ordered participants and winner; a simple self foreign key alone cannot express that full rule.

On this local MySQL 26.7 server, a direct-insert probe did not reject a missing self-referenced row, despite the declared self FK. Import correctness therefore relies on the explicit pre-write lineage validation and complete stored-row verification on rerun, rather than assuming that self FK enforces the policy. Direct SQL edits bypass application validation; there is no historical write API. No global server settings or broader account privileges were required.
